# 服务部署与脚本维护

状态：可复用流程与模板，未在用户目标服务器部署。所有示例名称、路径和账户均须替换并验收，不能视为某个历史项目的完整安装器。

## 发布前确认

记录操作系统、CPU 架构、.NET 目标框架、服务名、运行账户、端口、配置来源和当前发布版本。框架依赖发布需要目标机兼容运行时；自包含发布仍须选择正确 RID 和系统依赖。

先在隔离目录解包发布产物，校验来源、完整性与配置；保留上一版本和服务定义备份。配置与业务数据独立存放，不在覆盖程序时覆盖数据库、日志、密钥或持久化目录。

## Linux systemd 模板

同目录 [example.service](example.service) 是唯一 unit 模板。示例前提：

- 已有 `example` 用户和组；
- 程序位于 `/opt/example/current/Example.dll`；
- `/usr/bin/dotnet` 是目标机实际运行时；
- 应用以前台方式运行，将日志输出到标准输出 / 错误。

模板采用 Type=simple，不要求应用发送 systemd 就绪通知。若改为 Type=notify，必须同时实现并验证对应宿主集成。

安装到 `/etc/systemd/system/example.service` 后，先用 `systemd-analyze verify` 检查定义，再按 [[04_Troubleshooting/Linux/systemd服务管理]] 重载、启动和查日志。单元模板不会创建用户、开放端口或部署程序。

## 分阶段验收

1. **进程**：服务启动，未反复崩溃。
2. **监听**：实际地址、端口与访问范围一致。
3. **应用**：健康接口及必要鉴权按预期返回。
4. **依赖**：数据库、Redis、外部 HTTP 按应用身份连接成功。
5. **业务**：一次代表性处理完成，输出可核对；仅有 HTTP 200 或服务 active 不算端到端验收。
6. **恢复**：重启后状态合理，失败任务不会无限重复或重复产生业务结果。

可用 [inspect-service.sh](inspect-service.sh) 收集服务状态、日志及监听信息。它只读，不安装、不重启；日志可能含业务信息，分享前脱敏。本脚本仅做静态检查，未在目标 Linux 运行。

## 升级、失败退出和回滚

安装脚本先检查依赖、目录、权限和备份，任何关键步骤失败即退出；不要一边报错一边宣布成功。更新一份明确归属自己的服务或定时配置，重复运行不追加重复行。

维护窗口内切换到新发布目录并重启，完成上述验收后再清理过期版本。失败则切回上一发布目录和原配置，重启并重新验证。涉及数据库迁移时，程序回滚不等于数据回滚，须另有兼容迁移与恢复计划。

## Windows Service

Windows 安装应先确认程序已支持服务宿主生命周期，再注册服务；普通控制台程序不是注册后就一定能被服务管理器正常启动。记录服务账户、完整可执行路径、工作目录 / 内容根目录、运行时和恢复策略。配置和日志采用明确路径，避免服务从系统目录启动后找错文件。

本轮没有可核验的历史 Windows 安装器，因此保留步骤边界，不编造已成功的一键安装命令。
