# TCP 未连接、重连与资源生命周期

状态：历史未连接错误有用户日志；迁移到原生 .NET 8 的方案曾给出，但没有 Windows/Linux 双端实测成功证据。本篇只沉淀通用通信问题，不包含机器人控制流程。

## 现象与已知事实

历史对话「TCP Socket 未连接错误」在 2026-08-14、08-17 两次出现：

```text
The operation is not allowed on non-connected sockets.
TcpHelper.SendData(...)
```

同一时间有 Ping 成功信息。两者不矛盾：ICMP 可达不能证明应用持有的 TCP 连接仍可用。

仅在发送前读取 Connected 也不能保证下一瞬间发送成功；该属性反映最近一次 IO 的状态。[TcpClient.Connected 文档](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.tcpclient.connected?view=net-8.0)

## 排查顺序

1. 先用 [[02_Technology/Network/网络与代理分层排查]] 确认目标监听、地址及端口。
2. 从首次连接成功日志向后找断线、发送异常、对端关闭和重连记录；不要只截取持续报错的最后几行。
3. 检查是否多个定时器 / 线程同时执行连接、断开和发送。
4. 检查接收循环是否在读取 0 字节时退出并标记断开。
5. 记录连接代次或连接对象标识，核对旧接收任务退出时是否误关闭刚创建的新连接。

## 可沉淀的实现约束

- 用一个协调者管理连接状态和重连。重连循环避免重入，采用有上限的退避，并响应停止 token。
- 发送、断开和替换连接必须有一致的同步策略；发送失败更新状态，不能只写日志后继续把旧对象当连接成功。
- 每个连接拥有自己的接收任务和取消源；结束旧连接时只释放旧资源，不清空新连接。
- .NET 8 可通过支持 token 的 ConnectAsync 和 NetworkStream 异步读写控制取消 / 超时；不要靠同步 SendTimeout 期待异步写自动超时。
- TCP 是字节流，读到的一块数据不等于完整业务报文。按长度前缀、分隔符或协议格式积累解析，处理半包和粘包。
- 操作系统 KeepAlive 是辅助探测，不能替代业务心跳和确认；参数支持应分别在 Windows/Linux 验证。
- 写入成功仅说明本机发送流程未报错，不保证对端业务已经处理。断线重发需要业务去重或确认机制。

异步取消与锁释放的统一规则见 [[02_Technology/DotNet/后端配置与生命周期]]，本篇不复制整套帮助类。

## 故障注入验收

| 场景 | 期望 |
| --- | --- |
| 对端正常关闭 | 接收返回 0 后退出，进入重连 |
| 拔网线 / 丢包 | 在约定预算内发现异常，重连不堆积 |
| 并发发送并触发重连 | 不发生重复 Connect 或释放新连接 |
| 应用在重连期间停止 | 所有循环退出，不继续建连接 |
| 连续断开 / 恢复多轮 | 任务、句柄、内存不持续增长 |
| 重发业务消息 | 能识别已处理消息，避免重复效果 |

待补证据：所用包与运行时版本、两种操作系统的测试结果、断线检测耗时、停止日志。源码重构建议和 Git 提交说明不等于这些测试已经通过。
